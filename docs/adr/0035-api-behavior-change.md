# ADR-0035：发现 Moomoo API 行为可能变化时怎么处理

- **状态**：已定
- **日期**：2026-11-18
- **来源**：你 2026-11-18 的问题「Moomoo API 行为变了怎么检测、规避风险」与决定（都按建议）

## 决策

版本变化、返回数据出现新字段或新枚举值、基线字段消失时，系统怎么反应；谁来确认新版本可用

## 取值

1. **版本闸门**：`config/verified_versions.toml` 记下已验证的 OpenD 与 SDK 版本（含验证日期与依据）。`mooapp doctor` 不一致时 WARN；`mooapp run` 启动时比较：
   - SIMULATE：报警 `api_version_changed`，**继续运行**（OpenD 会自动升级，不打断每天的模拟盘验收）
   - REAL：**拒绝启动**（REAL 目前关闭，开放时生效）
2. **数据形状**：适配层把每个接口的返回字段与基线（探针录制，2026-11-12 ～ 11-16）比较，关键枚举与 vendor 文档的取值比较：
   - 新字段 `api_new_field`、基线字段消失 `api_field_missing`、新枚举值 `api_new_enum`：**只报警，不停交易**（每个进程每项只报一次）
   - 现有的保守处理不变：必需字段缺失或类型不对直接报错；映射不了的订单状态报 `unmapped_status`；不认识的市场状态按非常规时段拒单
3. **确认新版本**：由你更新 `verified_versions.toml`。版本变化后先重跑 `pytest -m sim tests/contract` 与相关探针，确认结论仍成立，再改文件并提交，提交说明写明依据；行为确有变化时先改代码、learnings 和基线

## 理由

系统的正确性建立在一系列实测结论上（learnings P1–P13）。版本闸门让「环境变了」被看见；字段与枚举比较让「数据形状变了」被看见；真正危险的 REAL 一律不在未验证的版本上运行。
